# feature-ideation

機能アイデアを広く出して Markdown の vault に貯め、効果・難易度・プロジェクト制約への整合でタグ付けし、
優先度を可視化する Claude Code プラグイン。

「1 つの機能をどう作るか」ではなく、**その前段の「どの機能を作るべきか」**を扱う。
`superpowers:brainstorming` が 1 feature を設計 → plan → 実装へ繋ぐのに対し、こちらは
アイデアを溜めて腐らせないための道具。

## インストール

### 1. マーケットプレイスを追加する

```
/plugin marketplace add alphabet-h/koshian-plugins
```

### 2. プラグインをインストールする

```
/plugin install feature-ideation@koshian-plugins
```

インストール後に `Run /reload-plugins to activate.` と表示されたら、`/reload-plugins` を実行する。
スキル一覧に `feature-ideation` と `check` の 2 つが出れば成功。

## 何ができるか

| スキル | 用途 |
|---|---|
| `/feature-ideation` | 引数なしでアイデア出しの 6 ステップを回し、vault に永続化する |
| `/feature-ideation discuss ID` | 既存アイデア 1 件を深掘りし、詳細ファイルへ昇格させる |
| `/feature-ideation archive ID [理由]` | 完了・却下を台帳へ移す |
| `/feature-ideation:check` | vault の状態サマリと陳腐化検出 |

「何かアイデアある？」「改善点ないかな？」のような発話でも自動で起動する。

## 使い方

```
「このプロジェクト、何か改善のアイデアある？」
        │
        ▼
  ┌───────────────────────────────────────────┐
  │ 1. プロジェクト探索                        │
  │    CLAUDE.md / README / TODO / 既存 vault  │
  │    → 非ゴールと value prop を掴む          │
  ├───────────────────────────────────────────┤
  │ 2. カテゴリ軸を 5〜8 個立てる               │
  │ 3. 各カテゴリで 5〜10 案                    │
  │    外部の事実は WebSearch で裏を取る        │
  │ 4. 推薦ピック + 意識的に後回し              │
  ├───────────────────────────────────────────┤
  │ 5. AskUserQuestion で方向性を合意 ← 一度停止 │
  ├───────────────────────────────────────────┤
  │ 6. docs/feature-ideas.md へ永続化           │
  │ 7. 次アクションを提示して停止                │
  └───────────────────────────────────────────┘
        │
        ▼  後日
  /feature-ideation:check
        │
        ├─ 件数を実数で集計（lib/vault-digest.sh）
        ├─ 再評価期限の超過 / 長期未確認
        ├─ vault ディレクトリの異物・孤児ファイル
        ├─ index と ADR の食い違い
        └─ 優先度ピックの改訂トリガ
```

`check` の集計は `lib/vault-digest.sh` が行う。件数と日付差はスクリプトが決定的に出し、
「次に手を付けるべき 3 件」や「index と ADR のどちらが正しいか」の判断だけをモデルが担う。

### 定期的に `check` を走らせる

このプラグインが解く問題の本体は「vault は増えるが見直されない」こと。
v0.1 は自動起動の hook を持たないので、外部から定期実行することを勧める。

```
/loop 1d /feature-ideation:check
```

または `/schedule` で週次のルーティンとして登録する。

## vault の構造

```
docs/
├── feature-ideas.md          # index + 再評価キュー + 優先度ピック + 台帳 2 表
├── feature-ideas/
│   ├── FI-002.md             # 深掘りした個別アイデア
│   └── archive-2026.md       # 台帳が 60 行を超えたときの年次退避
└── known-issues.md           # 発火条件つきの持ち越し（vault には入れない）
```

`docs/feature-ideas/` に置けるのは `FI-` か `archive-` で始まるファイルだけ。
実装計画は `docs/plans/`、仕様調査は `docs/specs/`、判断記録は ADR へ。
`check` がこの規約違反を検出する。

## 設計の背景

このプラグインは 2 つのプロジェクトで 4 ヶ月運用したローカルスキルを、そこで判明した摩擦を潰して
プラグイン化したもの。主な設計判断とその根拠は次のとおり。

| 判断 | 根拠 |
|---|---|
| ID をカテゴリ非依存の `FI-001` にした | カテゴリ再編で ID とカテゴリが恒久的に食い違う事象と、2 階層 ID の衝突が実際に起きた。ID は台帳や ADR から参照される外部キーなので、意味を持たせてはいけない |
| `起票日` 列を廃止した | 一度も遡及付与されず、一括ブレストでは 8 割が同一日になり停滞シグナルとして機能しなかった |
| 停滞判定を 3 層（vault 全体 / カテゴリ / 個別ファイル）に分けた | 行ごとの列は更新コストが作業量に比例せず、結果として捏造される。3 層ならどの層も実際に触った分だけ更新される |
| アーカイブを別ファイルではなく vault 本体に内蔵した | 別ファイル方式は 2 プロジェクト・4 ヶ月で一度も生成されなかった。「ファイル作成 + リンク + 棲み分け表更新」の 3 操作を要求したのが敗因 |
| 台帳の `証跡` と `知見` を空欄禁止にした | リンクを張らないと台帳行が書けないので、実装から vault へ戻る導線が構造的に強制される |
| 日付にできない持ち越しを vault の外へ出す | 「〜が出たら再評価」は日付比較では拾えないので、期限として書いた時点で誰にも気づかれず放置される |
| 集計をシェルスクリプトに寄せた | 「件数は実数で数えよ」と散文で戒めるより、機械が数えたほうが確実 |

## 前提

- **bash**（Windows では Git Bash）。`check` の集計スクリプトが依存する
- `superpowers` プラグインは**任意**。あれば設計フェーズへの引き渡しに使うが、無くても動く

## Roadmap

- **v0.1.0**（このリリース）— ルータ型スキル + `check` + 集計スクリプト + 新 vault フォーマット
- **v0.2.0（予定）**
  - `SessionStart` hook — 期限超過があるときだけセッション開始時に 1 行通知する。
    `check` を人間が呼ばないと期限に誰も気づかない、という v0.1 最大の弱点への構造的な対策
  - `harvest` — git log / TODO コメント / 落とし穴 KB からアイデア候補を自動収穫する
  - `promote` — idea から plan への昇格と、index への戻りリンクの自動記入
