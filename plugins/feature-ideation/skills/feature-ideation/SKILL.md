# Feature Ideation

「どの機能を作るべきか」を決める前段を担う。アイデアを広く並べ、効果・難易度・プロジェクト制約への
整合でタグ付けし、`docs/feature-ideas.md`（もしくはユーザ指定パス）の vault に永続化する。

**使い分け**: 作るものが 1 つ決まっていて仕様を詰めるなら `superpowers:brainstorming`。
まだ何を作るか決まっていないなら本スキル。迷ったら本スキルで方向を確定させてから渡す。

## 引数による分岐

| 引数 | 動作 |
|---|---|
| (なし) | 下の「デフォルトワークフロー」を実行する |
| `discuss ID` | [`references/discuss.md`](references/discuss.md) を読み、その手順に従う |
| `archive ID [理由]` | [`references/archive.md`](references/archive.md) を読み、その手順に従う |
| 上記以外 | 「`discuss` / `archive` のいずれかか、引数なしで起動してください」と案内して中止する |

vault の状態確認（件数・期限超過・停滞）は本スキルではなく **`check` スキル**が担当する。
「進捗どう？」「棚卸ししたい」と言われたらそちらへ案内する。

## デフォルトワークフロー

既存 vault があるなら**まず Read してから**始める。

### 1. プロジェクト探索

目的は **現状・制約・非ゴールの把握**。これを怠るとアイデアが「あったら便利」止まりになり、
プロジェクトの value prop に抵触する案を無駄に量産することになる。

存在するものだけ読む: `CLAUDE.md` / `README.md` / `TODO.md` / `ROADMAP.md` / `docs/plans/` /
`package.json`・`Cargo.toml`・`go.mod` 等 / **既存 vault**（重複追加を防ぐため必ず読む）。

**特に探すもの**: 明示的な**非ゴール・借用判断の原則・value prop**。「単体バイナリ維持」
「外部サービス依存なし」「オフライン動作」のような不変条件が、あとの `⚠️` / `❌` 判定の根拠になる。
明文化されていなければ README の価値提案と既存の技術選定から類推する。

現在の effort は `${CLAUDE_EFFORT}`。これが xhigh か max なら、探索範囲を広げて設計ドキュメントや
テストまで読み、制約の根拠を具体的に掴む。

### 2. カテゴリ軸の選定

プロジェクト種別に応じて **5〜8 個**。少なすぎるとアイデアが薄く、多すぎると並べる手間が上回る。

推奨デフォルト（再構成してよい）: 中核品質の強化 / 周辺連携・クライアント特化 / 入力と対応範囲の多様化 /
品質・運用基盤 / UX 小粒 / 他ツールからの輸入候補 / 研究的ネタ。
性格に応じてセキュリティ・i18n・アクセシビリティ・onboarding などを足してよい。

### 3. アイデア生成

各カテゴリ **5〜10 項目**が目安。思いつかないカテゴリは 2〜3 項目で終わってよく、無理に埋めない。
評価軸の意味とタグの付け方は [`references/evaluation.md`](references/evaluation.md)。

現在の effort は `${CLAUDE_EFFORT}`。これが xhigh か max なら、カテゴリごとに視点を変えて掘り下げる
（コードの痛点 / 競合の機能 / 運用の穴 / ユーザの言葉）。

**外部の事実は今このセッションで裏を取る。** 「類似ツール X にこの機能がある」「ベンチで N% 改善した」
のような外部事実をモデルの記憶から書いてはいけない。記憶にある機能一覧は古いか存在しない。
WebSearch / WebFetch で確認し、**URL を残す**。確認できなければ書かないか「未確認」と明示する。
vault は長期参照される資産で、しかもアイデアという性質上あとから検証されにくい。
ここで混入した誤りは長く残る。

### 4. 推薦ピック

**「次に手を付けるなら」個人的ベット順**を 5〜7 項目、なぜその順序かの一文付きで示す。
バンドルできる軽量 feature はまとめて 1 項目にしてよい。
あわせて **「意識的に後回し」** を 2〜3 項目、理由付きで挙げる。

### 5. 方向性の合意（ここで一度止まる）

`AskUserQuestion` で聞く。

- どのカテゴリ / 項目が刺さったか（複数選択）
- 動機はどれに近いか — 自分の使い勝手 / 他人に配りたい / 具体的に困っている / OSS 的な差別化

ユーザが動機を言わずカテゴリだけ指定したら、そのまま次へ進んでよい。

### 6. 永続化

**既存ファイルがある場合**: merge する。ID 衝突を避けて新規項目を該当カテゴリに追記し、
優先度ピックを日付付きで更新する。**既存のカテゴリ編成と ID を尊重し、勝手に付け替えない**。

**無い場合**: [`references/template.md`](references/template.md) を雛形にして作成する。
プロジェクト不変条件・棲み分け表・カテゴリ表を埋める。ID は `FI-001` から通しで振る。

### 7. 次アクションの提示

選択肢を出すだけに留める。ユーザが選ぶまで待つ。

- 推薦トップを設計フェーズへ（`superpowers:writing-plans` が使えるならそれに渡す。無ければ通常の設計フロー）
- 該当 ID を `discuss` で深掘り
- `TODO.md` に相互リンクを 1 行追加
- そのまま停止（ユーザが何も指定しなければこれを選ぶ）

## 絶対に守ること

- **実装フェーズへ勝手に進まない。** このスキルは vault を作るだけ。step 7 で提案はしてよいが、
  ユーザが選ぶまでコードも計画も書かない
- **外部の事実を記憶から書かない。** 裏を取って URL を残す（step 3）
- **既存 vault を破壊的に書き換えない。** 既存 ID は台帳・ADR から参照される外部キーなので付け替えない
- **条件トリガ型の持ち越しを vault に入れない。** 「〜が出たら」「〜の検証後」は日付に落とせないので、
  期限として書いた時点で誰にも気づかれず放置される。逃がし方は
  [`references/archive.md`](references/archive.md) の「条件トリガの隔離」
- **下流が動いたら index に戻る。** ADR を書いた、plan 化した、実装した — そのとき vault の行も更新する。
  実運用で GO 判定から実装完了まで 2 時間で走った案件が、index 上では「未判定」のまま数週間残った

## アンチパターン

- **カテゴリ粒度の不揃い** — 1 カテゴリに 20 項目、他が 1 項目では分割が悪い。5〜10 に均す
- **根拠のないスコア** — 「効果 大」だけで理由なしは価値が薄い。備考に一行入れる
- **網羅せねば症候群** — 全カテゴリを無理に埋めると薄いアイデアが並ぶ
- **備考の青天井** — 200 字を超えたら詳細ファイルへ昇格する（[`references/evaluation.md`](references/evaluation.md)）
- **評価の上書き** — `⚠️` → `✅` のように判定が動いたら、古い評価を消さず詳細ファイルの
  `## 判定履歴` に日付付きで追記する。上書きすると同じ議論を将来もう一度やることになる
