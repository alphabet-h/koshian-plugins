# vault テンプレート

`docs/feature-ideas.md`（もしくはユーザ指定パス）を新規作成するときの雛形。
`<...>` はプロジェクトに合わせて埋める。**実在しないパスは棲み分け表に書かない**（壊れリンクになる）。

書式は `idea-check` の集計契約でもある。装飾や見出しを勝手に変えると件数と期限検出が壊れる。
契約の一覧は本ファイル末尾の「idea-check との契約」を参照。

---

````markdown
---
title: "<Project> Feature Ideas"
last_sweep: YYYY-MM-DD   # 全行を実装状態 (コード / CHANGELOG / 外部仕様) と突合した最終日
---

# <Project> Feature Ideas

これから検討したい改善候補の **vault**。効果・難易度・制約整合で優先度を判断し、
着手したものは末尾の台帳へ移す。**このファイルは実装計画を持たない**（→ 棲み分け表）。

**プロジェクト不変条件**: <value prop / 非ゴールを 1〜3 行。例: 「Markdown のディレクトリに 1 バイナリを
置くだけで RAG 化」＝ 外部ランタイム依存を増やさない>
これを壊す候補は 制約 `⚠️` / `❌` として扱う。

## 既存 doc との棲み分け

| パス | 役割 | vault との関係 |
|---|---|---|
| `<docs/feature-ideas.md>` (本ファイル) | アイデアの index + 台帳 2 表 | — |
| `<docs/feature-ideas/>FI-NNN*.md` | 個別アイデアの**詳細ファイル**（論点・採用条件・判定履歴） | 備考からリンク |
| `<docs/plans/>` | **実装計画** | vault ディレクトリに置かない。備考からリンク |
| `<docs/specs/>` | 仕様調査・要件（取得日つきの外部仕様を含む） | 同上 |
| `<docs/decisions/>` | ADR（判断の固定記録） | 台帳の `証跡` からリンク |
| `<docs/known-issues.md>` | **発火条件つきの持ち越し**（「実害が出たら」「要望が出たら」）の指定席 | vault からは出す |
| `<TODO.md / CHANGELOG.md>` | 実装済み履歴 | 実装済み台帳と二重管理しない |

## 凡例

| 列 | 値 | 意味 |
|---|---|---|
| ID | `FI-001` | カテゴリ非依存の通し番号。**一度振ったら変えない**（台帳・ADR から参照される外部キー） |
| （移行時） | `id_style: categorical` | frontmatter に書くと `A-1` 形式の ID をそのまま集計できる。既存 vault を ID を付け替えずに移す場合に使う（後述） |
| 状態 | `idea` | 起票済み・未着手（既定値） |
| 状態 | `probing` | 深掘り中。詳細ファイルあり、採否は未決 |
| 状態 | `planned` | spec / plan を書いた。実装フローへ引き継ぎ済み |
| 状態 | `frozen` | 発火条件待ち。期限を持たない（こちらから判断できない） |
| 効果 | 大 / 中 / 小 | 大 = 中核指標が数値で動く / 中 = 痛点が減る / 小 = あると便利 |
| 難易度 | 低 / 中 / 高 / 極高 | 低 = 半日〜1 日 / 中 = 数日 / 高 = 1〜2 週 / 極高 = 月単位・既存アーキに侵襲的 |
| 制約 | ✅ / ⚠️ / ❌ | プロジェクト不変条件を壊さないか。`⚠️` は**昇格条件を備考に必ず書く** |
| (任意) 依存 | crate / サービス | 新規依存の有無が採否の一次基準になるプロジェクトのみ 8 列目に追加 |

**表記の規律**（崩れると `idea-check` の集計が壊れる）

- 状態は上記 4 語を**装飾なし**で書く（`**done**` `✅ done` のような揺れを作らない）
- `done` / `declined` は index に残さない。**行ごと台帳へ移す**（墓標行を作らない。ID の欠番は台帳 2 表で説明がつく）
- 備考は **200 字以内**。超えたら詳細ファイルへ昇格し、備考は「一行要約 + リンク」にする
- **日付つきの追記は詳細ファイルの `## 判定履歴` へ書く。備考に履歴を積まない**
- 「1 行に複数アイテム」を作らない。一部だけ終わったら完了分を台帳へ移し、**残余に新しい ID を切る**
- `依存` 列を採るなら全カテゴリ表で統一する。**9 列以上にはしない**

## 再評価キュー

**日付で書けるものだけ**をここに置く。「〜が出たら」「〜の検証後」のような発火条件しかないものは
vault ではなく `<known-issues.md>` へ（更新ルール 8-10 参照）。

| 期日 | ID | 何を判定するか | 判定材料 |
|---|---|---|---|
| YYYY-MM-DD | FI-002 | <例: hook 経由の前処理で ✅ に昇格できるか> | <例: 2 週分の trial-log> |

- `期日` は `YYYY-MM-DD` のみ。相対表現（「2〜3 週間後」）も条件文も書かない
- **`何を判定するか` を空にしない**。日付だけの期限は、その日が来ても何を決めるのか分からず腐る
- 判定したら**この行を削除**し、結論は詳細ファイルの `## 判定履歴` に日付つきで残す

## 優先度ピック (YYYY-MM-DD 版)

**「次に手を付けるなら」個人的ベット順**

1. **FI-00N (名前)** — 一文で理由（なぜこの順序か）
2. **FI-00M + FI-00K (バンドル名)** — 一緒に扱える軽量 feature 束
3. ...

**意識的に後回し**

- **FI-00X (名前)** — 理由（YAGNI / ペイオフが薄い / 基盤 X が整ってから 等）

**改訂トリガ**（いずれか成立したら選び直す。`idea-check` が検出して提案する）

- **T1** 前回ピックから **90 日**経過
- **T2** ピック項目の**過半数**が done / declined になった
- **T3** 前回ピック以降に **10 件以上**の新規アイデアを追加した
- **T4** **ピックに載っていない ID が実装済み台帳に入った**（ピックが実態から乖離している合図）

> 履歴は**直近 2 版まで**本文に残す。それ以前は削除してよい（完了項目は実装済み台帳が正本）。

## 実装済み台帳

実装・出荷済みの候補。詳細な経緯は参照先が正本。

| ID | 名前 | 完了日 | 証跡 | 知見 |
|---|---|---|---|---|
| FI-00N | <名前> | YYYY-MM-DD | <PR #123 / v0.12.0 / ADR-0004 のうち 1 つ以上> | <詳細ファイル or knowledge note へのリンク、または 1 行の学び> |

- **`証跡` は空欄禁止**。PR 番号 / タグ・version / commit / ADR のいずれかを最低 1 つ。
  判断が覆った場合や不可逆な決定を含む場合は ADR も併記する
- **`知見` は空欄禁止**。実装で分かったこと（特に**起票時の想定が外れた点**）を 1 行で書くか、
  詳細ファイル・knowledge note へリンクする。ここが埋まらないと、実装で得た知識が vault に戻ってこない。
  **既存 vault から移行した行はこの限りではない**（当時の記録に学びが残っていないことがある）。
  空欄禁止は移行後に新しく積む行にのみ適用する
- 新しい行は**先頭に追記**（完了日の降順）

## 不採用の記録

見送った候補。**復活条件を満たしたら該当カテゴリ表へ戻してよい**。物理削除はしない（議論の節約のため）。

| ID | 名前 | 判定日 | 理由 | 復活条件 |
|---|---|---|---|---|
| FI-00M | <名前> | YYYY-MM-DD | <なぜ見送ったか。統合なら「統合: FI-0NN と重複、出典は FI-0NN 備考へ移設」> | <何が起きたら戻すか。見込みがなければ `—`> |

- 重複 / alias / 上位項目への統合もこの表で扱う（3 本目の表は作らない）
- 台帳 2 表の合計が **60 行**を超えたら `<feature-ideas/>archive-<年>.md` に年次で切り出す

---

## 更新ルール

1. 新しいアイデアは**ペンディング**欄に自由記述で追記してよい。ID 付与は後でよい
2. 「やるかもしれない」段階で ID を振ってカテゴリ表へ（状態 `idea`）。
   **次の ID = max(index + 台帳 2 表) + 1**。欠番は再利用しない
3. 備考が 200 字を超える / 論点・URL・コード断片が要る → `<feature-ideas/>FI-NNN.md` へ昇格し、状態を `probing` に。
   備考は「一行要約 + リンク」に置換する。**評価が動いたときの日付つき追記は詳細ファイルの `## 判定履歴` へ**
4. `<feature-ideas/>` 直下のファイル名は **`FI-` か `archive-` で始まる**こと。
   実装計画は `<docs/plans/>`、仕様調査は `<docs/specs/>`、ADR は `<docs/decisions/>` へ置く
5. **孤児を作らない** — `<feature-ideas/>` の全ファイルは index か詳細ファイルから最低 1 本リンクされること
6. 再評価の時期を**自分で決められる**なら再評価キューへ日付で書く。
   **外部条件待ちなら vault から出して `<known-issues.md>` へ**（どうしても出せないときのみ状態 `frozen` で残す）
7. 実装・出荷したら**行ごと実装済み台帳へ**、見送ったら**行ごと不採用の記録へ**移す
8. カテゴリを棚卸したらそのカテゴリの `最終確認` を更新。**全行を突合したときだけ** frontmatter の `last_sweep` を更新する
9. 外部プラットフォーム前提（他ツールの機能等）を条件にした行は、棚卸のたびに公式 docs を引き直す
10. vault を更新したら末尾の**変更履歴**に 1 行追記する

---

## ペンディング (未整理のアイデア)

- _(ID を振る前のアイデアはここに自由記述で追記)_

---

## 変更履歴

<vault 自身の更新ログ。1 セッション 1 行、新しい順。「最近何が動いたか」はここで分かる>

- **YYYY-MM-DD**: <例: 全行棚卸。done 5 件を台帳へ、統合 2 件を不採用の記録へ。カテゴリを 1 つ解体>
- **YYYY-MM-DD**: <例: FI-045〜FI-052 を新規追加（UX 小粒カテゴリ）>
````

## idea-check との契約

テンプレの「装飾禁止」「見出し書式の固定」は、すべて `idea-check` が機械的に集計するための契約。
プロジェクトごとに崩してよい部分と、崩してはいけない部分を分けておく。

| # | 契約（崩さない） | パターン |
|---|---|---|
| 1 | ID | `FI-` + 3 桁数字（`id_style: categorical` なら英字 1〜2 + `-` + 数字） |
| 2 | index の状態 | `idea` / `probing` / `planned` / `frozen` のみ（装飾なし） |
| 3 | vault 全体の棚卸日 | frontmatter `last_sweep: YYYY-MM-DD` |
| 4 | カテゴリの確認日 | カテゴリ見出し直下の斜体行に `最終確認 YYYY-MM-DD` |
| 5 | アイテムの最終更新 | 詳細ファイル frontmatter `updated:` と実ファイルの mtime |
| 6 | 期限 | `## 再評価キュー` 表の `期日` 列（`YYYY-MM-DD` のみ） |
| 7 | ピック改訂日 | 見出し `## 優先度ピック (YYYY-MM-DD 版)` |
| 8 | 台帳 | `## 実装済み台帳` = 5 列（`証跡` / `知見` 非空）、`## 不採用の記録` = 5 列 |
| 9 | 詳細ディレクトリ | 直下は `FI-NNN...` か `archive-YYYY...` のみ（categorical なら `A-9...` 等） |

崩してよい部分: カテゴリの数・名前・順序、`依存` 列の有無、備考の書き方、プロジェクト不変条件の書き方。

## 既存 vault からの移行（`id_style`）

旧形式の vault は ID がカテゴリ依存（`A-1` / `C-7` 等）になっていることが多い。
`FI-NNN` へ付け替えるのが本来の形だが、**ID は台帳・ADR・knowledge note・ソースコードの
doc コメントから参照される外部キー**なので、実運用の vault では付け替えコストが数百箇所に達し、
同じ表記が別の名前空間（spec の設計判断 ID、audit の指摘 ID）と衝突していることもある。

そこで frontmatter に次を書くと、**ID を付け替えずにそのまま集計できる**。

```yaml
---
title: "<Project> Feature Ideas"
id_style: categorical
last_sweep: YYYY-MM-DD
---
```

- 詳細ファイル名の規約も `A-9-...md` のように追随する
- 外部参照の検出も同じ形式で行われる（`feature-idea` 修飾つきのみを拾う規律は変わらない）
- 宣言しないまま `A-1` 形式の行があると、集計対象外になったことと宣言方法が警告として出る

**新規に作る vault では使わない。** カテゴリ再編で ID とカテゴリが食い違う問題は
`FI-NNN` でしか解決しない。

`idea-check` はテーブルのヘッダ行を読んで列名から位置を決めるので、**列の順序が違っても動く**。
ただし列名（`ID` / `状態` / `名前` / `効果` / `難易度` / `制約` / `備考`）は変えないこと。
