## 評価軸の意味

評価は**同一プロジェクト内での相対比較**であって絶対基準ではない。

| 軸 | 値 | 意味 |
|---|---|---|
| 効果 | **大** | ユーザ体感が明確に変わる。中核指標（検索精度・処理速度等）が数値で動く |
| 効果 | **中** | 使い勝手が改善される、痛点が減る |
| 効果 | **小** | あると便利だが無くても困らない |
| 難易度 | **低** | 100 LOC 未満 / 半日〜1 日 |
| 難易度 | **中** | 数百 LOC / 数日 |
| 難易度 | **高** | 設計論点あり / 1〜2 週間 |
| 難易度 | **極高** | 研究的 / 月単位 / 既存アーキに侵襲的 |
| 制約 | **✅** | プロジェクトの不変条件（value prop / 非ゴール）に抵触しない |
| 制約 | **⚠️** | 条件付き採用可。**昇格条件を備考に必ず書く** |
| 制約 | **❌** | 不採用候補。議論の節約のために記録だけ残す |

**なぜ制約が重要か**: プロジェクトには大抵「XX しないこと」という不変条件がある（単体バイナリ維持、
外部サービス依存なし、オフライン動作 等）。これを壊す提案は、いくら良くても採用されない。
早期にマークすることで議論のエネルギーを採用可能な範囲に集中できる。

**`⚠️` の書き方**: 「どう料理すれば ✅ に昇格するか」が読めないと議論にならない。
「サーバ自身が LLM を呼ぶなら ❌ だが、前処理を hook 経由にすれば ✅」のように**昇格経路**を書く。

**`効果 大` だけ書いて理由がない項目は価値が薄い**。備考に一行「なぜその評価か」を入れる
（例: 「公表値で失敗率 35-50% 改善」）。ただし外部の数値は、**その場で裏を取って URL を残す**こと
（記憶から書かない）。

## 難易度を読み違えやすいケース

- **「既存に足すだけ」に見えて設計論点があるもの** — 既存の抽象が想定していない軸を足す場合、
  実装は小さくても設計は重い。迷ったら 1 段上げる
- **外部依存が絡むもの** — ライブラリ追加はコード量ゼロでも、ライセンス・メンテ状況・バイナリサイズの検討が乗る
- **「あとで戻せない」もの** — データ形式・公開 API・ファイル配置の変更は、LOC が小さくても難易度は高く扱う

## 範囲表記を単一値に倒すとき（移行時）

旧 vault には `中〜大` `小〜中` `低〜中` のような範囲表記が混ざっていることがある。
新形式の集計は単一値を前提としているので倒す必要があるが、**倒す向きを揃えないと後から読めない**。

> **効果は下に、難易度は上に倒す。** 期待値を膨らませない側であり、
> 上の「難易度は迷ったら 1 段上げる」とも向きが揃う。

規則に反する向きへ倒すなら、**その行だけ理由を残す**。倒し方の一覧を vault の凡例の下か
`## 変更履歴` に置いておくと、後から 1 行ずつ検算できる。

同じ範囲表記（例: 2 行とも `中〜大`）が別方向に解決されているのに理由が書かれていないと、
読んだ人はどちらが誤りか判断できない。**同じ入力が別の出力になった箇所は必ず記録する。**

## 備考: インラインのまま OK か、詳細ファイルへ昇格か

index の備考欄は**短く保つ**のが原則。詰めるほど長くなるので、以下で判断する。

### インラインのまま OK

- 1 行（〜80 字）で評価根拠が書ける
- `⚠️` の昇格条件が一行で書ける
- 比較対象が 1 つだけ + 短い参照

### 詳細ファイル `FI-NNN.md` へ昇格

以下のいずれかに該当したら切る。

- 複数の論点 / 条件分岐を書く必要が出てきた
- 複数の引用 / URL を入れたい
- コード断片や設定例を含む
- `discuss` で詰めた結果、3 段落以上の議論になった
- インラインに書くと **200 字**を超える

昇格したら index の備考は「一行要約 + リンク」に置換し、状態を `probing` にする。

## 評価が動いたときは詳細ファイルの判定履歴へ追記する

「なぜ今この評価なのか」は、**評価が変わった履歴**を見ないと分からない。上書きすると同じ議論を将来もう一度やる。

ただし**追記先は index の備考ではない**。備考に日付つき追記を積むと、詳細ファイルが既にあっても
index のセルが膨れ上がる（実運用で 1,200 字に達した例がある）。「200 字以内」と「履歴を消さない」は
追記先を分けることで初めて両立する。

- **index の備考**: 常に**最新の一行要約 + リンク**だけ。上書きしてよい
- **詳細ファイルの `## 判定履歴`**: 追記専用。日付つきで新しい順に積む

```markdown
## 判定履歴

- **2026-07-25**: NO-GO 確定。閾値が想定の 3 倍と判明しシグナル 4 が不成立
- **2026-05-18**: Phase 2-pre / 2-main に細分化。GO シグナル 4 + NO-GO 3 を策定
- **2026-05-03**: 起票。⚠️（前処理の置き場所が未定）
```

詳細ファイルがまだ無い段階で評価が動いたら、そのとき詳細ファイルを切る。

## 詳細ファイルの書式

`<feature-ideas>/FI-NNN.md`（または `FI-NNN-<slug>.md`）。複数アイデアを束ねるなら `FI-006+FI-009-<slug>.md`。

```markdown
---
id: FI-012
title: "<一行タイトル>"
status: probing        # index の 状態 と一致させる
created: YYYY-MM-DD    # このファイルを作った日
updated: YYYY-MM-DD    # 中身を触るたびに更新する
category: "<index の見出し名>"   # 任意
related:                          # 任意。相対パス
  - ../plans/<...>.md
---

# <title>

## ひとことで
<1〜3 行。index の備考に貼るのはこの要約>

## 背景 / 発端
<なぜ起票したか。外部事実には URL を必ず付ける>

## 論点
<選択肢 A/B/C、条件分岐、トレードオフ>

## 採用条件 / 却下条件
<何が起きたら ✅ / ❌ になるか>

## 判定履歴
<追記専用。日付つき、新しい順>

## 未解決の問い
- [ ] <次に読んだ人が最初に答えるべき問い>

## 参照
```

- `updated` は `idea-check` が「詰めたのに判定していない項目」を拾うためのシグナル。
  実ファイルの mtime が裏を取るので、更新を忘れても劣化動作する
- `id` / `status` は index の写し。**正本は index** で、不一致は `idea-check` が報告する
- `tags` は入れない（スキルが使わないラベルが増殖する）。Obsidian 運用のプロジェクトは任意で追加してよい
- **「既存 doc との棲み分け」表を詳細ファイルにコピーしない**。棲み分けは vault 本体の単独責任
- サブ項目を作るときは `FI-012-a` のように**親 ID を前置**する。局所 ID 単独（`R-1` 等）は使わない。
  サブ項目が 10 を超えたら、それは 1 アイデアではなく計画なので複数の `FI-` に分割するか vault の外へ出す
